# Инструкция по рефакторингу — geomarketing-platform

> Рабочий документ. Обновляется при отклонениях от плана.
> Изменения кода — только по явному разрешению владельца проекта.

## 1. Цели
1. Достичь результата уровня «глубокая переработка» (декомпозиция god-классов,
   слои, устранение дублирования, безопасность, наблюдаемость).
2. Не сломать работающий функционал (auth, бренды, компании/карточки/группы/шаблоны).
3. Сохранить **полную обратную совместимость HTTP-API** api-gateway.
4. Повысить читаемость, тестируемость, поддерживаемость (Clean Code, SOLID, DRY, KISS, YAGNI).

## 2. Контекст (зафиксировано на интервью)
- **Production нет** — только dev-стенд (деплой на VPS есть, но реальных пользователей/данных нет).
- Целевая глубина: **C** (глубокая), исполнение — в дисциплине **B** (тесты вперёд, мелкие обратимые этапы).
- **Полная BC HTTP-API — обязательна.**
- Разрешено: добавлять миграции, менять существующую схему БД, обновлять зависимости, добавлять тесты и тест-инфраструктуру.
- Скоуп map-parser — уточняется (по умолчанию **вне скоупа**).

## 3. Правила безопасности (жёсткие)
- Не менять публичные контракты из раздела 12 без отдельного согласования.
- Один этап = одна логически завершённая группа изменений; не смешивать
  (рефакторинг ≠ обновление зависимостей ≠ миграции ≠ форматирование).
- Минимальный diff; не переписывать рабочий код целиком без необходимости.
- Не удалять код, пока не доказано, что он не используется.
- Не добавлять `any` ради прохождения сборки; не отключать тесты/проверки.
- Секреты не логировать и не выводить в отчётах (маскировать).
- После каждого этапа — прогон проверок (раздел 13); при новой ошибке — стоп.

## 4. Порядок анализа (выполнено)
README/доки → package.json → tsconfig/eslint → docker-compose/Dockerfile →
CI → .env.example → структура → точки входа → контроллеры/сервисы →
DTO/сущности → миграции → фильтры/guard/интерсепторы → контракты RMQ.

## 5. Выбранная стратегия
**B → цель C.** Сначала характеризационные тесты фиксируют текущее поведение,
затем безопасные фиксы, безопасность, индексы, декомпозиция, унификация, логгер.

## 6. Этапы рефакторинга
- Этап 0 — тест-инфраструктура + characterization-тесты. *(в работе)*
- Этап 1 — быстрые безопасные фиксы (логи, STATUS_TO_CODE, RPC-хелпер).
- Этап 2 — безопасность (CORS-allowlist, rate-limit, SESSION_SECRET, чистка логов).
- Этап 3 — миграция индексов.
- Этап 4 — декомпозиция CompanyService.
- Этап 5 — унификация логики полей карточки.
- Этап 6 — структурный логгер + correlation-id.
- Этап 7 — (опц.) полный strict TS.

## 7. Требования к тестам
- Перед изменением поведения кода — характеризационный тест, фиксирующий текущее.
- Не менять одновременно реализацию и ожидание теста.
- Обязательное покрытие критических сценариев (раздел 11) до Этапа 4.
- Тесты: unit на чистую логику (сборка карточки, slug, маппинг ошибок, формат ответа).

## 8. Правила обратной совместимости
Без отдельного согласования не менять: URL, HTTP-методы, коды ответов,
структуры request/response, имена JSON-полей, обязательность полей, форматы дат,
enum-значения, RMQ-паттерны/очереди, имена env, схему/имена таблиц и колонок.
При необходимости смены контракта — сначала: причина, старый/новый контракт,
риски, план миграции, период совместимости, откат.

## 9. Правила журнала
Все действия фиксируются в `REFACTORING_LOG.md`. Секреты/токены/пароли/содержимое `.env` не записываются.

## 10. Критерии завершения
- Все запланированные этапы закрыты или явно отложены.
- `yarn build`, `tsc --noEmit`, `eslint` (без `--fix`), тесты — зелёные.
- HTTP-контракты идентичны зафиксированным снапшотам.
- Журнал заполнен, риски описаны.

## 11. Критический функционал (не сломать)
- Регистрация/логин/логаут/`/me`, смена профиля/аватара/пароля, сброс пароля.
- Бренды: CRUD + slug + права доступа (владелец).
- Компании: список (пагинация/поиск), создание, просмотр, удаление, `main_data`.
- Карточка: `PATCH /companies/:id/default`, значения по умолчанию/переопределения.
- Шаблоны, группы, платформы компании, импорт из 2ГИС, загрузка файлов.

## 12. Публичные контракты (беречь)
- HTTP-эндпоинты api-gateway + заголовки `x-brand-id`, `x-timezone`.
- Формат ответа `{success,data}` / `{success:false,error:{code,message,details?}}`.
- RMQ-паттерны (`libs/contracts/patterns.ts`), очереди (`queues.ts`).
- Имена контейнеров, env-переменные, схема БД.

## 13. Команды проверки (read-only)

## 14. Карточки проблем (детально)

### SEC-001 — CORS отражает любой Origin + credentials
- Приоритет: High · `apps/api-gateway/src/main.ts:49-66`
- Риск текущего: любой сайт делает аутентифицированные запросы с кукой юзера.
- Вариант A (реком.): allowlist origin из env + `enableCors`. Риск: Medium (согласовать список origin).
- Проверка: запрос с доверенного/недоверенного origin; фронт логинится как прежде.

### SEC-002 — нет rate-limit на логине/сбросе
- Приоритет: High · `auth.controller.ts` (`login`, `forgotPassword`)
- Вариант A (реком.): `@nestjs/throttler` (новая зависимость). Риск: Low.
- Проверка: >N запросов → 429; обычный логин работает.

### SEC-003 — SESSION_SECRET fallback/optional
- Приоритет: Medium · `main.ts:82-83`, `libs/config/src/env.validation.ts:30`
- Вариант A (реком.): в prod обязателен (fail-fast), убрать хардкод-fallback.

### SEC-004 — логирование секретов
- Приоритет: Medium · `auth.controller.ts:59,63,116`, `session.guard.ts:12`, `main.ts:34-41`
- Вариант A (реком.): удалить/понизить до debug без чувствительных полей.

### ARCH-001 — god-класс CompanyService (725 стр.)
- Приоритет: High · `apps/core-service/src/company/company.service.ts`
- Вариант B (реком.): выделить `CompanyTemplateService`, `CompanyGroupService`,
  `CompanyPlatformService` + `CardAssembler`, `SlugGenerator`; фасад сохраняет RMQ-хэндлеры.
- Проверка: characterization-тесты get/create/updateDefault/группы; паттерны и формы ответов идентичны.

### ARCH-002 — дублирование RPC-boilerplate в контроллерах
- Приоритет: High · все контроллеры api-gateway
- Вариант A (реком.): хелпер `RpcClient.send(pattern, payload, timeout?)`. Риск: Low.

### ARCH-003 — два алгоритма слияния полей карточки
- Приоритет: Medium · `assembleCardFields` vs `resolveForPlatform`
- Вариант A (реком.): общий модуль `card-fields` с явными правилами приоритета.
- Проверка: табличные unit-тесты (шаблон/override/платформа/isException/lang-merge).

### ARCH-004 — пустой logger, неструктурные логи
- Приоритет: Medium · `libs/logger/src/logger.service.ts`
- Вариант A (реком.): structured logger (JSON) + correlation-id; заменить `console.log`.

### ARCH-005 — дубль STATUS_TO_CODE
- Приоритет: Low · оба фильтра gateway
- Вариант A (реком.): вынести карту и `codeFromStatus` в общий модуль.

### DB-001 — отсутствие индексов
- Приоритет: High · сущности/миграции core
- Индексы-кандидаты: `companies(brandId)`, `companies(brandId,status)`,
  `company_platforms(platformKey,orgId)`, `company_defaults(companyId)`,
  `company_defaults(templateId)`, `company_group_members(groupId)`,
  `company_group_members(companyId)`, `company_templates(brandId)`, `company_groups(brandId)`.
- Вариант A (реком.): новая миграция `AddIndexes` (только CREATE INDEX). Риск: Low.

### DB-002 — generateSlug: последовательные SELECT + гонка
- Приоритет: Low · `company.service.ts:698`
- Вариант A: оставить (уник-констрейнт защищает), обернуть повтор при 23505.

### TS-001 — неполный strict
- Приоритет: Medium · `tsconfig.json:21-22` (`noImplicitAny:false`, `strictBindCallApply:false`)
- Вариант A: поэтапно включить `noImplicitAny`, затем полный `strict` (поздний этап).

### TS-002 — `any` в сессии/req
- Приоритет: Low · `main.ts`, контроллеры
- Вариант A: типизировать `express-session` (declaration merging для `userId/role`).

### REL-001 — хардкод таймаута, нет retry
- Приоритет: Medium · контроллеры
- Вариант A: вынести таймаут в конфиг; ретрай — только для идемпотентных чтений (отдельно).

### TEST-001 — нет тестов
- Приоритет: Critical (для рефакторинга) · весь проект
- Вариант A (реком.): characterization-тесты критических путей (Этап 0).

## 15. Процедура отката
- Каждый этап — атомарный коммит в ветке `refactor/foundation-and-safety`.
- Откат этапа: `git revert <commit>` или откат перечисленных в журнале файлов.
- Миграции: `yarn migration:revert` (по одной).
- Новые зависимости откатываются вместе с коммитом этапа.
